# Satchel topics, and why they are shaped this way

A topic is a subject that memories hang off. It can be small, like the monitoring tool, or it can be an effort with an outcome, a brief and work to do. A topic with a repository link or tasks is what used to be called a project. It can have zero, one or several code repositories. It is the scope that memories, tasks and grants hang off, so almost every other decision in Satchel bottoms out here. `docs/topics.md` is the model.

The database and the code say topic too: the `topics` table, `topic_id`, `topic_repositories`, `upsert_topic`, `src/features/topics/`. They were renamed in `20261009090000_topics_everywhere.sql`, generated by `scripts/generate-topics-rename.mjs` (D35). Older migrations keep the names they were written with.

## The one paragraph version

A topic is a row with a stable UUID, a slug, a name, a brief and a revision. Personal scope is the absence of a topic: `topic_id is null`, everywhere, in every table. A topic may link GitHub repositories, one repository to at most one topic per owner. A conversation picks an active topic for itself only, either explicitly or by a short-lived repository hint staged from the local Git origin. Picking never expands a grant. Creating never expands a grant either, which is why the `upsert_topic` tool returns `grant_required`.

The overnight pass may make a topic too (`create_satchel_topic`, `made_by = 'satchel'`). A nightly tidy moves work facts out of personal (`move_memory`) and merges duplicate topics it made (`merge_topic`, undone with `unmerge_topic`, recorded in `topic_merges`). A merged topic keeps its row with `merged_into` set and is left out of `service.topics()`. An app may only merge away a topic Satchel made, and never one with tasks or repositories.

## The rules that outrank convenience

**Personal is `topic_id is null`, everywhere.** Not a magic UUID, not a row named "Personal". Tasks give it a non-null `scope_key` of `'personal'` for composite foreign keys, but the scope itself is the null. An unknown scope must never default to personal. The tools call the same thing `topic_id: null`.

**A topic is not a repository.** It can have none. It can have several. A repository maps to at most one topic, because the link is per owner and exclusive. Nothing creates a repository when you make a topic, and no repository is required to make a task.

**Repository linking is routing, never authorization.** Resolving `owner/name` to a topic can only reach a link whose topic is already in the connection's grant. RLS exposes nothing else. A link is a shortcut for "which topic am I in", not a permission.

**Selecting a topic is session-local.** `agent_session_scopes` is keyed by `(owner_id, client_id, session_key)` and carries the grant generation. It changes this conversation and nothing else, and it is invalidated the moment the generation rotates.

**Creating a topic does not grant access to it.** An agent with write capability can create one, and then cannot read it. `upsert_topic` returns `grant_required: true` so the agent can say so out loud instead of failing mysteriously later. A connection granted every topic (`all_topics`) can use it straight away, and the tool says `false`.

**Every topic write is revision-checked and idempotent.** `expected_revision` omitted means create; supplied means update, and a mismatch is `PT409`. `topic_write_requests` keys `(owner_id, request_id)` to a payload hash, so the identical retry returns the stored result and a reused ID with a different payload is refused.

**Deleting is a person's action, and it says what it took.** `delete_topic` is companion-only, revision-checked, and returns the counts of memories, tasks and files removed. It also drops the topic from every connection's `topic_ids`.

## When you change something

1. Anything that changes what a scope means is a migration and a decision, not a refactor. `docs/topics.md` is the product model and `docs/decisions.md` is the ledger.
2. A new scope kind starts with the domain union and an intentional migration. Unknown scopes must not fall back to personal.
3. If you touch the hint bridge, re-read `references/traps.md` first: it is the only anonymous write surface in the product.
4. `npm test` and `npm run build` pass before a push.

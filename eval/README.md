# Retrieval evaluation

A labelled corpus and a harness for measuring memory retrieval. This is the baseline any change to retrieval gets measured against.

```bash
node eval/embed.mjs     # cache embeddings, needs a local ollama, nothing leaves the machine
node eval/run.mjs       # the report, compared against the committed baseline
```

`run.mjs` exits non-zero when a system regresses more than 0.02 utility against `baseline.json`, so it can gate a change.

| Flag | Does |
|---|---|
| `--slices` | per-category breakdown, which is where you see what a change actually moved |
| `--update-baseline` | adopt the current numbers. Only after reading them. |

## Why utility is the headline number

Two systems cannot be compared on relevance alone, because a system that stays silent more often scores worse on every relevance metric while being better to use. So the single number is:

- a prompt **with** an answer scores its nDCG@10
- a prompt **with no** answer scores 1 if the system stays quiet, 0 if it injects something

averaged over every prompt. It is only as honest as the ratio of answerable to answerless prompts in the corpus, so the report prints that ratio next to it.

Everything else is still reported. nDCG, R@5 and MRR say how good the answers are; coverage and silence say how often it speaks when it should and shuts up when it should.

## Significance

Every interval is a seeded bootstrap over prompts, 2000 resamples. Comparisons are **paired**, so they test the change rather than the variation between prompts.

A difference whose interval includes zero is reported as `noise` and should be treated as no difference. On a corpus this size most differences between vector configurations are noise. Reporting three decimals does not make them real.

Because the seed is fixed, two runs of the same code print the same numbers, and a diff means something changed.

## The corpus

One invented person: a Bengaluru software engineer with work codebases, side projects, tax admin, running, knee rehab, sourdough, film photography, a flat move, a Schengen visa, a wedding and a Goa trip. Nothing in it is real.

It was generated by agents given the schema and a quality bar, and no knowledge of the retrieval design. That matters: a corpus written alongside the query is a corpus that agrees with the query.

```
projects[]  slug, name, brief
tasks[]     slug, project|null, title, status, closed_at|null
memories[]  id, statement, source, band, project|null, task|null, edge_case?, supersedes?
prompts[]   id, text, context, category
```

**Ids are stable and permanent.** Nothing is keyed by array position, so the corpus can grow without invalidating a single label. `merge.mjs` assigns fresh ids and never moves an existing one.

### Edge cases the memories cover

`supersession` (a newer memory contradicting an older one), `near-duplicate` (the same fact for a different project, so retrieving the wrong one is a real error), `identifier` (a version pin or table name with almost no prose), `very-short`, `numeric`, `people`, `task-dependent` (meaningless without its task), `half-opinion`.

### Prompt categories

Answerable: `paraphrase` (shares no words with its answer), `identifier`, `code-mixed` (Hinglish), `typo`, `rambling`, `style-only` (only writing preferences are relevant), `cross-domain`, `temporal`.

Answerless: `continuation` (no topic at all), `uncovered` (a fair question the corpus cannot answer), `lexical-trap` (strong vocabulary overlap with a memory, unrelated meaning), `general-knowledge`, `fresh-topic`.

The traps and the continuations are what make the floor measurable. A system that answers them is injecting noise.

## Labels

`labels.json`, keyed by prompt id.

- **2** the assistant would be wrong, or would have to ask, without this memory
- **1** genuinely useful, but the answer is not wrong without it

Produced by agents labelling disjoint slices of the prompts against the whole memory set, with no knowledge of any retrieval method. When the corpus grows, `run.mjs` refuses to run until every prompt is labelled, because an unlabelled prompt silently counts as answerless and corrupts the one number the corpus exists to produce.

## Adding to it

1. Write prompts or memories as JSON in the shape above.
2. `node eval/merge.mjs <file.json>` assigns ids and refuses anything referentially broken.
3. Label the new prompts. If you added memories, recheck the existing prompts against them, because a new memory can answer an old prompt.
4. `node eval/embed.mjs` embeds only what is new.
5. `node eval/run.mjs`, read it, then `--update-baseline`.

Prompts with no correct answer are the most valuable thing to add, and the hardest to write. Lexical traps most of all.

## What this has found

Recorded in [docs/memory-v2-build.md](../docs/memory-v2-build.md) section 4.

The short version: `websearch_to_tsquery` returns nothing for most prompts because it ANDs every term; `ts_rank_cd` cannot rank because it has no corpus statistics; summed IDF ranks correctly but no lexical score thresholds usefully; vectors beat lexical by a real margin while hybrid over pure vector is noise; a 3x scope multiplier needs to be right 87% of the time to break even while 1.1 captures the same benefit; demoting closed-task memories is contradicted by the labels; and the cosine gate is **per model**, not a shared constant.

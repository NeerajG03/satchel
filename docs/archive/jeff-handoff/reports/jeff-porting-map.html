Design note · JEFF rethink

Where each piece of JEFF goes

JEFF today is a Go CLI on one Mac that runs agents. The rethink is one portable store of tasks, memory, skills, and personas that any agent on any device can reach. This note takes every piece JEFF has right now and says where it lands.

15 pieces mapped 4 verdicts: keep · move · replace · drop written for Neeraj, 2026-09-05

I want to be upfront about the test I used for every piece. It is the phone test you gave me. If I open Claude on my phone, or a fresh laptop, or a cloud session, does this piece still exist and still help? If yes, it stays. If it only exists because a Go binary on one volume created it, it has to move or go.

And one more thing I kept coming back to. A lot of JEFF is plumbing that Claude Code and Codex now do natively, and a smaller part is the idea nobody else will build for you. The idea is the store. The plumbing is everything that runs an agent. So the pattern below repeats a lot: content stays, storage moves to git, the CLI dies.

Work

Tasks

Move
Today

  • tasks, subtasks, deps, comments, checkpoints, events, attrs
  • about 25 open tasks, 6-char IDs like gig-58bc

After
  • GitHub Issues on one private hub repo, not on the code repos
  • subtasks become sub-issues, deps become blocked-by links
  • comments and checkpoints are issue comments
  • every device and every agent already speaks gh
gig.dbSQLite, one Mac
→
gig exportJSONL, already exists
→
hub repo Issuesone issue per task

The gig data model is good. I would keep the shape and change only where it is written. GitHub Issues gives me almost every field gig has, and the two it does not have, checkpoints and attrs, fit as a templated comment and as labels.

Why a separate hub repo and not the code repos? Because your tasks span backend, frontend, and api-automation at once. If the issue lives on backend, the frontend PR has nowhere natural to point. One hub repo means one issue, and each code repo's PR says Closes you/hub#123.

The gig CLI itself can go two ways. It can die, and you use gh issue directly. Or it stays as a thin wrapper that talks to the GitHub API but keeps the commands you have muscle memory for. I lean to letting it die. The MCP server covers the agent side, and gh covers you.

The one thing to check first. The Jeff-Anywhere epic found that gig's claim is get-then-update, so two agents can both "win" a claim. GitHub's assignee field has the same problem in theory. But in practice one person plus a few agents on one board rarely collide, and the MCP claim_task tool can check assignee before setting it. I feel that is good enough. If it is not, that is the one reason to keep a tiny hub server owning the claim.

Repo registry

Move
Today
  • jeff.json lists 10 repos with url and description
  • per-repo base_branch, a branch-name.sh, and post_setup scripts
  • a SessionStart hook prints the list into every agent's context
After
  • repos.yaml in the hub repo: name, url, one-line description
  • MCP exposes it as a resource so any agent can ask "what repos exist"
  • branch naming and post-setup move into each code repo itself

The descriptions are worth keeping. They are the thing that lets an agent on your phone say "that sounds like a python-backend change." The scripts are not worth keeping in JEFF. A repo's own setup belongs in that repo, in a CLAUDE.md or AGENTS.md plus a setup script, where every tool that clones it will find it. Codex and Claude Code both run repo setup from the repo now.

This is the clearest drop. Isolation per task is now a checkbox in the vendor app. The one thing you lose is the multi-repo desk, one folder with three worktrees in it. I cover that under what you lose. Short version: one issue, several sessions, PRs link back.

Pickup, work, done

Replace
Today
  • jeff pickup claims, builds the desk, injects hooks, skills, memory, launches the agent
  • jeff work resumes from the last checkpoint
  • jeff done closes the task and tears down the desk
After
  • open any session, say "pick up hub#123"

jeff pickup gig-58bcone Mac, one binary
→
"pick up hub#58"any client, MCP does the rest

Pickup is really three things glued together: claim the task, load the right context, start an agent. In the new shape the agent is already started, that is the session you are typing into. Claim and load context become one MCP tool call that any client can make. So the command becomes a sentence.

Checkpoints

Keep
Today
  • gig checkpoint --done --next --blockers
  • a nudge hook fires after git commit, gh pr create, jeff ship
  • injected on resume so the agent knows where it stopped
After
  • same three fields, written as an issue comment with a fixed header
  • MCP checkpoint tool, so the phone can write one too
  • nudge stays a native Claude Code hook in your user settings

This is the piece I would protect most. Vendor sessions are machine-local. The checkpoint is the only thing that lets a session on your laptop tomorrow continue what a session on your phone did tonight. It seems to be the real cross-device resume story, more than any memory system. Keep the template exactly, just change where it is written.

Ship

Drop
Today
  • jeff ship pushes every branch on the task and opens PRs in every repo
After
  • the session opens its own PR, both apps do this in one prompt
  • convention: PR body ends with Closes you/hub#123
  • the hub issue shows all linked PRs across repos automatically

Ship was a loop over repos calling gh pr create. Each session now does its one repo. The cross-repo view you had from ship, "three PRs for this task", GitHub gives you on the issue page for free once the PRs reference it.

Context

Hooks

Replace
Today
  • 6 shell scripts on SessionStart: gig instructions, ready tasks, jeff instructions, repo list, task context, crew inbox
  • PostToolUse checkpoint nudge
  • only run where the jeff binary installed them
After
  • an MCP server sends instructions to every client that connects, so that replaces the "here is how to use gig" text
  • ready tasks, repo list, task context become MCP resources or tool results
  • checkpoint nudge stays a native hook in ~/.claude/settings.json, synced with your dotfiles

Almost all your hooks do one job: paste text into the agent's context at start. MCP has a built-in way to do that. When a client connects to a server, the server can hand over instructions and a list of resources. So the hook scripts become a few strings inside the server, and they show up on the phone too, which the scripts never could.

The crew inbox hook goes away with crew. The nudge hook is the one real hook left, and Claude Code hooks are the right home for it.

Skills

Replace
Today
  • 25 skills under .skills/, each a SKILL.md plus scripts
  • skills.json registry with tags and persona lists
  • jeff skill add / inject / eject / tag / new, a lock file
  • a uv venv so skill scripts run
After
  • one git repo, you/skills, same folders, same SKILL.md files
  • npx skills add you/skills installs into Claude Code, Codex, Cursor, Gemini, opencode in one go
  • npx skills update and check replace the lock file
  • MCP exposes the same SKILL.md files as resources for the phone
jeff skill injectcopies into one task dir
→
npx skills add you/skillsany agent, any machine

Yes, npx skills is simpler and I think it is the right call. It does the exact thing your registry did, install the same skill folder into several agents' skill directories, and it is maintained by someone else. The 25 skills are the asset. The registry, the inject and eject commands, and the lock file were only there because there was no shared installer. Now there is.

Two things I would keep from your side. First, the skills that need Python keep their pyproject.toml in the skill folder so uv run works after install. Second, the persona-to-skill mapping in skills.json moves into each persona file, as a plain list. That is the only bit of the registry with real information in it.

Where npx skills stops. It installs into a filesystem. Your phone has none. So on Claude mobile the skills do not "install." Two honest options: the MCP server serves SKILL.md as a readable resource so the agent can still read the procedure, or you upload the same skills to claude.ai's own skills feature and accept a second copy to keep in sync. I would start with the MCP resource and see if it is enough. Scripts will not run on the phone either way, and I think that is fine, the phone is for thinking and small edits, not for running Langfuse queries.

Personas

Keep
Today
  • 6 personas: doug, eric, hardy, jenko, marlowe, schmidt
  • each has a PERSONA.md, a preferred model, a memory hint, and a list of skills
  • each has its own memory scope, hardy has 8 entries

After

  • in Claude Code they map one-to-one onto subagent definitions

Personas are pure content, so they survive whole. What changes is only how they get applied. Claude Code has subagents with a name, a model, a tool list, and a system prompt in a markdown file. That is a persona. A short script can generate .claude/agents/hardy.md from personas/hardy.md so you keep one source. Codex and opencode have their own profile files and the same generator can write those.

Marlowe is special. It is not a worker persona, it is the curator, and it becomes the scheduled routine under memory.

This is the piece the whole rethink is for, so I want to be careful. The design you already have is right: proposals from many, one curator, canonical entries with scope and provenance. All of that survives. What was wrong is only that it lived on a volume, and that the write path needed a shell hook.

MCP fixes both paths at once. Any client that can connect to the server can search memory and propose memory. That is the phone. That is a cloud session. That is Codex. And the single-writer rule survives because the routine is the only thing with a token that can push to memory/.

What I would drop

The transcript queue. 344 sessions waiting and no curation has ever run. Transcripts are big, machine-local, and mostly noise. I feel the honest move is to keep only explicit proposals. If an agent learned something, it says so with one tool call. If it did not say so, it is gone, and that is okay.

What I would test before building

Whether curated memory changes anything. You have 68 entries. Before writing the server, take ten real tasks and check if any of those entries would have changed the outcome. If the answer is mostly no, build the task side first and the memory side later. If yes, memory goes first.

One limit I cannot design around. claude.ai and Claude Code each have their own memory, and I cannot write into them from outside. So your store wins only if the session is told to check it first. In Claude Code that is one line in CLAUDE.md. On the phone it is the server's connect instructions. It is a prompt, not a guarantee, and I would rather say that plainly than pretend.

Move
Today

  • jeff project init / list / open

A project is a folder with a CLAUDE.md. Git is the way to make a folder exist on more than one machine, so each one becomes a repo. Small, private, boring. Interviews and intern logs have people's information in them, so those stay private and I would not put them in the hub repo itself, just link them from it.

The one thing this loses is the single list. jeff project list showed them all. repos.yaml with a kind field gives that back, and the MCP resource reads the same file.

Running

Crew and orchestrator

Drop
Today
  • workers in tmux windows, an orchestrator session, crew.db
  • send, ack, interrupt, events, a live dashboard
  • a good share of your open tasks are about keeping this working
After
  • parallel work: Claude Code fleet view, the Agent tool, cloud sessions, Codex threads
  • the shared board: hub issues, assignee, and comments
  • talking to a running agent: the vendor's own UI, or Slack via Claude in Slack

This is the hardest one to say and I think it is right. Crew was built when there was no way to run several agents and see them in one place. Now there is. And crew is the part of JEFF that generates the most bugs about itself: liveness, tmux windows closing, hooks emitting empty output, a stub provider.

What crew really gave you, underneath tmux, was a shared task board that several agents read and write. That is exactly what hub issues are. Two agents on two machines both see the same issue, the same assignee, the same last comment. The messaging layer, send and ack, becomes an issue comment mentioning the assignee, which is slower but works from a phone.

I would keep the crew-orchestrator skill's behavioral guidance, the part about assessing tasks and coordinating. That is a persona for whoever runs the board. The Go code goes.

The provider flag existed so one launcher could start any brain with the same context. In the new shape you never launch anything. You open the vendor's app and it connects to your store. Being provider-neutral stops being code you maintain and becomes a property of the protocols you picked.

Loose folders

Move
Today

  • research/ and exports/, notes and generated artifacts
  • transcripts/, 157 saved sessions
  • a dozen one-off scripts and reports in the JEFF root
After

None of this needs a design. It needs an afternoon with a bin. The learnings are the only ones I would read before deleting, because they are the raw material memory was supposed to be built from.

What you lose, honestly

  • The multi-repo desk. One folder with three worktrees in it, one agent touching all three. In the new shape that is one issue and three sessions, or one session that clones two repos side by side. It is a little more clicking. I think it is worth it, but it is a real loss.
  • Fast agent-to-agent messaging. Crew send and ack were near-instant. Issue comments are slower and rely on the agent checking. If you truly run five agents that need to talk to each other in real time, the vendor tools are not there yet either.
  • Memory injection you control fully. Today session-start edits the agent's settings and turns off native memory. You will not be able to do that on the phone. Your store is a strong suggestion, not the only voice.
  • Skills scripts on the phone. The phone can read a skill but not run its script. Phone sessions become thinking and small edits.
  • A small always-on server. The MCP server has to run somewhere with a public URL and auth. It is far less code than JEFF today, but it is ops, and ops is a kind of maintenance too.

This is not the Jeff-Anywhere epic

You already have an epic filed for making JEFF work from anywhere. I read it, and I want to be clear that this note points a different way, so you can pick one and not drift between them.

Jeff-Anywhere epic

JEFF becomes the fleet. A hub owns the gig store and hands out claims. Headless jeff worker processes on several machines dial in, build workspaces, run agents with -p, and stream back. Slack is the chat client. Five phases.

You own the hub, the workers, the protocol, the leases, the context packs, and the Slack app.

This note

Vendors are the fleet. A git repo owns the store. A small MCP server exposes it. Claude Code, Claude mobile, Codex, and cloud routines are the workers, and they already exist and already have chat UIs.

You own a repo, a skills repo, and one small server with about seven tools.

The epic was written when the vendor apps could not do multi-session, remote, or scheduled work. They can now. So most of what the epic builds, the hub, the worker daemon, the WebSocket protocol, the context packs, is the same plumbing this note says to drop. The one idea from the epic I would keep is the single writer for memory, and it lands as the curation routine.

Order of moves, not dates

Each step is useful on its own, and each one lets you delete something. I put the cheapest and most certain first.

  1. Skills repo plus npx skills. Push .skills/ to you/skills, run npx skills add you/skills on this Mac and one other. Delete the registry, inject, eject, and lock file. Zero risk, immediate win, and it proves the multi-agent install works.
  2. Tasks to GitHub Issues. gig export to JSONL, a short script creates one issue per open task on a new private hub repo with sub-issues and labels. Keep closed tasks as a JSONL file in the repo for history. Point your PRs at Closes you/hub#N. Stop using gig.
  3. Memory, personas, repos.yaml into the hub repo. Straight file moves. Fold learnings/ in or delete it. Drop the transcript queue. Generate .claude/agents/*.md from personas/.
  4. MCP server, read only. search_memory, get_context, list_ready_tasks, get_task, and connect instructions. Host it, connect Claude Code and Claude mobile. This is the first moment the phone test passes.
  5. MCP server, writes. propose_memory, claim_task, checkpoint, close_task. Now a phone session can pick up work and leave a checkpoint.
  6. Curation as a routine. Marlowe runs on a schedule in a cloud session, reads proposals/, commits to memory/. First curation ever runs.
  7. Retire the Go CLI. Pickup, worktree, crew, orchestrator, ship, doctor, config. Archive the repo. Close the JEFF-on-JEFF tasks.

The calls only you can make

  • Issues or files for tasks? I lean Issues. Files in git are simpler to own but worse for many writers and have no UI on the phone. Issues have both.
  • Public or private skills repo? Some skills name internal systems, Langfuse hosts, MongoDB, Temporal. Private unless you scrub them.
  • Where the server runs. A home Mac with a tunnel, a small VPS, or a serverless host. Any works. Pick the one you will not forget about.
  • Whether memory goes before or after tasks. Depends on the ten-task test under memory. I would run it before deciding.
  • Whether to keep gig as a thin CLI. Muscle memory versus one fewer thing to maintain. I lean to letting it go.
